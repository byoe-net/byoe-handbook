## 1. PDEVI 是什么？

**PDEVI** 是 BYOE 内置的**结构化 AI 编程工作流**，由 5 个英文单词首字母组成：

```
P — Plan      计划  （告诉 AI 要做什么）
D — Design    设计  （AI 提出技术方案）
E — Execute   执行  （AI 写代码实现）
V — Verify    验证  （确认代码是否正确）
I — Iterate   迭代  （发现问题，循环改进）
```

你可以把 PDEVI 理解为一位**有方法论的 AI 开发搭档**：

> 不是你说什么它就做什么，而是它会先想清楚再动手，并且帮你记住每一步进展。

---

## 2. 为什么需要 PDEVI？

### 直接对话 AI 的问题

| 问题 | 表现 |
|------|------|
| 容易跑偏 | AI 自己发挥，做出你不需要的东西 |
| 没有记忆 | 每次对话都要重新解释背景 |
| 无法追踪 | 不知道哪些完成了、哪些没完成 |
| 出错难回溯 | 代码改坏了不知道从哪里看起 |

### PDEVI 解决了什么

| 解决方案 | 效果 |
|----------|------|
| 强制先写 proposal.md | AI 在动手前必须明确目标和范围 |
| 分阶段确认 | 你在每个关键节点可以叫停或调整 |
| 文件持久化 | 关掉浏览器重新打开，进度还在 |
| 内置 Iterate 阶段 | 遇到问题不是重来，而是循环修复 |

## 3. 快速准备（5 分钟）

### 第一步：安装 BYOE

```bash
pip install byoe
```

### 第二步：配置 API Key

```bash
# 选择你使用的模型提供商之一
export OPENAI_API_KEY=sk-...
# 或
export DEEPSEEK_API_KEY=sk-...
```

> **Windows 用户**：在 PowerShell 中使用 `$env:OPENAI_API_KEY = "sk-..."`

### 第三步：进入你的项目目录

```bash
cd /your/project        # 进入你的项目文件夹
```

> 如果还没有项目，先创建一个：`mkdir my-project && cd my-project`

### 第四步：初始化 Crew 工作区

```bash
byoe init
```

成功后你会看到：

```
✓ INSTRUCTIONS.md  已创建
✓ crew.yaml        已创建
✓ crew/            目录已创建
```

### 第五步：启动 BYOE

```bash
byoe web
```

浏览器会自动打开 Web UI，你就可以开始了！

## 5. P — Plan（计划）

### 这个阶段做什么

AI 会分析你的需求，生成一份结构化的计划文档：`crew/changes/<功能名>/proposal.md`

### proposal.md 包含什么

```markdown
## 目标
做什么，为什么做

## 范围
包含哪些改动，不包含哪些

## 验收标准
怎样算做完了（可测试的条件）

## 风险
可能遇到的问题
```

### 如何触发 Plan 阶段

**方式一：命令行**
```bash
byoe plan "login-feature"
```

**方式二：Web UI**
1. 点击左侧 **Crew** 面板
2. 在「新建变更」输入框填写功能名称（英文，用连字符）
3. 选择模式（新手推荐：标准）
4. 点击**创建变更**

**方式三：自然语言**
在对话框直接说：
```
帮我做一个用户登录功能，需要支持邮箱和密码登录
```

### 你需要做什么

1. 阅读 AI 生成的 `proposal.md`
2. 确认「验收标准」是你真正想要的
3. 如有不对，直接在聊天中说："第2条验收标准改为..."
4. 满意后，在 Crew 面板点击 **✓ 确认计划**

> ⚠️ **重要**：不确认计划，AI 不会进入下一阶段。这是一道防护关卡。

---

## 6. D — Design（设计）

### 这个阶段做什么

AI 根据 proposal.md 制定具体的技术方案，生成 `crew/changes/<功能名>/design.md`

### design.md 包含什么

```markdown
## 技术决策
用什么框架/库/方案，为什么

## 受影响的文件
列出所有需要新建或修改的文件

## 实现步骤
1. 步骤一
2. 步骤二
...

## 测试计划
如何验证功能正确
```

### 你需要做什么

1. 检查「受影响的文件」列表是否合理
2. 确认「技术决策」符合你的技术栈
3. 如有问题，直接告诉 AI："不要用 X，改用 Y"
4. 确认无误后，继续即可（Design 阶段无需手动确认，直接进入执行）

### 可以跳过 Design 吗？

可以。使用 `--express` 模式（适合 Bug 修复）：
```bash
byoe plan "fix-login-bug" --express
```
Express 模式跳过 D，直接从 P 到 E。

---

## 7. E — Execute（执行）

### 这个阶段做什么

AI 按照 design.md 的任务清单，逐步编写代码、修改文件。

### 如何启动执行

**方式一：点击 Crew 面板的「🤖 让 AI 执行」按钮**

按钮会自动构建这样的提示词发给 AI：
```
请按照 crew/changes/login-feature/design.md 执行任务清单中的步骤。
当前状态见 crew/resume.md。
```

**方式二：自然语言**
```
开始执行登录功能
```

### 执行过程中你能做什么

| 操作 | 方式 |
|------|------|
| 查看 AI 在改哪个文件 | 状态栏显示「N 个文件改动」，点击查看 |
| 暂停执行 | 发送：「先停一下，我有个问题」 |
| 修改方向 | 发送：「这个函数的实现改成用 async/await」 |
| 查看进度 | 发送：「现在做到哪一步了？」|

### AI 工具调用说明

执行阶段 AI 会使用以下工具（这是正常的，不要惊慌）：

| 工具名 | 作用 |
|--------|------|
| `read_file` | 读取现有代码 |
| `write_file` | 创建新文件 |
| `edit_file` | 修改现有文件 |
| `bash` | 执行命令（如安装依赖） |
| `search_files` | 搜索代码库 |

---

## 8. V — Verify（验证）

### 这个阶段做什么

AI 执行完成后，进入验证阶段：
1. 运行测试
2. 检查是否满足 proposal.md 中的验收标准
3. 报告结果

### 如何触发验证

**方式一：在聊天中说**
```
运行测试，验证登录功能是否正确
```

**方式二：在 Crew 面板点击「✓ 标记完成」**

点击后 AI 会自动检查所有验收标准。

### 验证通过后

1. Crew 面板显示绿色 ✓ 状态
2. 点击**归档**，将本次变更移入 `crew/archive/`
3. 功能完成！

### 验证失败了怎么办？

别慌，这很正常。BYOE 会自动进入 **Iterate（迭代）** 阶段。

---

## 9. I — Iterate（迭代）

### 这个阶段做什么

针对验证失败的问题进行修复，然后重新执行 → 验证，直到通过。

### 迭代流程

```
验证失败
   │
   ▼
AI 分析失败原因
   │
   ▼
AI 修复代码（回到 E 阶段）
   │
   ▼
重新验证（回到 V 阶段）
   │
   ├── 通过 → 归档完成
   └── 失败 → 继续迭代
```

### 安全机制

BYOE 有内置保护，防止无限循环：

| 情况 | BYOE 的行为 |
|------|------------|
| Express 模式 Verify 失败超过 3 轮 | 自动升级为 Standard 模式，强制 Design 阶段 |
| Standard 模式 Iterate 超过 5 轮 | 创建 `[OPEN]` 阻塞项，暂停等待人工介入 |

### 人工介入

当出现 `[OPEN]` 阻塞项时，说明 AI 卡住了。这时你可以：

```bash
byoe status          # 查看阻塞项详情
```

或在聊天中说：
```
看看 blockers.md，帮我分析为什么一直失败
```

## 10. 三种工作模式

根据不同场景，BYOE 提供三种模式：

### 标准模式（Standard）— 推荐新手使用

```bash
byoe plan "功能名称"
# 或
byoe plan "功能名称" --standard
```

**流程**：P → D → E → V → I

**适用场景**：
- 新功能开发
- 重大重构
- 不确定如何实现的任务

**优点**：最完整，有设计阶段保证方案合理性

---

### 快速模式（Express）

```bash
byoe plan "功能名称" --express
# 含 fix/hotfix/bug 关键词时自动使用此模式
byoe plan "fix-login-null-pointer"   # 自动 Express
```

**流程**：P → E → V（跳过 Design）

**适用场景**：
- Bug 修复
- 小改动（改个文案、调个样式）
- 紧急热修复

---

### 原型模式（Prototype）

```bash
byoe plan "功能名称" --prototype
# 含 poc/spike/prototype 关键词时自动使用
byoe plan "poc-new-algorithm"        # 自动 Prototype
```

**流程**：P → D → E（跳过 Verify，宽松约束）

**适用场景**：
- 快速验证想法可不可行
- 技术调研
- 不需要生产级质量的实验

---

### 模式对比

| 特性 | Standard | Express | Prototype |
|------|:--------:|:-------:|:---------:|
| Plan（计划） | ✅ | ✅ | ✅ |
| Design（设计） | ✅ | ❌ | ✅ |
| Execute（执行） | ✅ | ✅ | ✅ |
| Verify（验证） | ✅ | ✅ | ❌ |
| Iterate（迭代） | ✅ | ✅（上限3轮） | ❌ |
| 适合新手 | ⭐⭐⭐ | ⭐⭐ | ⭐ |

## 11. Crew 面板操作手册

Crew 面板位于 Web UI 左侧，点击「Crew」标签展开。

### 面板结构

```
┌─────────────────────────┐
│  Crew 工作区             │
│  ─────────────────────  │
│  📋 活跃变更 (2)         │
│                         │
│  ▶ login-feature        │
│    阶段: Execute         │
│    [🤖 让AI执行] [✓完成] │
│                         │
│  ▶ fix-bug-123          │
│    阶段: Verify          │
│    [✓标记完成] [归档]    │
│                         │
│  ─────────────────────  │
│  🚧 阻塞项 (1)           │
│  ─────────────────────  │
│  [+ 新建变更]            │
└─────────────────────────┘
```

### 按钮说明

| 按钮 | 功能 | 何时出现 |
|------|------|---------|
| **🤖 让 AI 执行** | 自动构建执行提示词发给 AI | Execute 阶段 |
| **✓ 确认计划** | 确认 proposal.md，允许进入下一阶段 | Plan 阶段 |
| **✓ 标记完成** | 触发验证流程 | Verify 阶段 |
| **归档** | 将变更移入 `crew/archive/` | Verify 通过后 |
| **查看** | 在侧边栏查看 proposal.md / design.md | 任意阶段 |
| **删除** | 永久删除变更（不可恢复） | 任意阶段 |

### 新建变更（界面操作）

1. 在「新建变更」输入框填写名称（只用英文字母、数字、连字符）
2. 选择模式：标准 / 快速 / 原型
3. 点击**创建变更**
4. AI 立即开始 Plan 阶段

## 12. CLI 命令速查表

所有操作都可以用命令行完成，也可以用 Web UI 完成。

### 初始化

```bash
byoe init                         # 初始化 Crew 工作区（项目根目录执行）
```

### 创建变更

```bash
byoe plan "功能名称"               # 标准模式
byoe plan "fix-xxx" --express     # 快速模式
byoe plan "poc-xxx" --prototype   # 原型模式
```

### 查看状态

```bash
byoe status                       # 查看所有活跃变更和阻塞项
```

### 归档

```bash
byoe release "功能名称"            # 归档已完成的变更
```

### 启动

```bash
byoe web                          # 启动 Web UI（推荐）
byoe web --port 8080              # 自定义端口
byoe chat                         # 纯命令行模式
```

### 自然语言替代命令

你不必记住上面所有命令，直接在对话框说：

| 你说的话 | 等价命令 |
|---------|---------|
| 帮我看看现在项目进度 | `byoe status` |
| 开始做登录功能 | `byoe plan "login-feature"` |
| 这个需求先不做了 | `byoe cancel <name>` |
| 把登录功能标记为完成 | `byoe release "login-feature"` |

## 13. 真实案例：从零完成一个登录功能

以下是一个完整的操作演示，包含你需要输入的每一句话。

### 准备工作

```bash
cd ~/my-web-project
byoe init
byoe web
```

---

### 第 1 步：创建变更（Plan 阶段）

在 BYOE 聊天框输入：

```
帮我做一个用户登录功能：
- 支持邮箱 + 密码登录
- 登录成功后跳转到 /dashboard
- 登录失败显示错误提示
- 使用 JWT token
```

AI 会生成 `proposal.md`，内容大致如下：

```markdown
## 目标
实现用户登录功能，包含 JWT 认证

## 验收标准
1. 邮箱格式验证通过后才能提交
2. 密码错误时显示「邮箱或密码不正确」
3. 登录成功后 localStorage 存储 JWT token
4. 登录成功后跳转 /dashboard
5. token 过期后自动跳转到登录页
```

**你要做的**：阅读验收标准，觉得 OK 就在 Crew 面板点击「✓ 确认计划」。

如果有问题，比如：

```
第5条先不做，太复杂了
```

AI 会更新 proposal.md，去掉第5条，再次请你确认。

---

### 第 2 步：查看技术方案（Design 阶段）

确认计划后，AI 自动生成 `design.md`：

```markdown
## 受影响的文件
- src/pages/LoginPage.tsx      （新建）
- src/api/auth.ts              （新建）
- src/store/authStore.ts       （新建）
- src/App.tsx                  （修改，增加路由）

## 实现步骤
1. 创建 LoginPage 组件（表单 + 验证）
2. 创建 auth.ts API 函数
3. 创建 Zustand authStore
4. 在 App.tsx 增加 /login 路由
```

**你要做的**：检查文件列表对不对，没问题就继续。

---

### 第 3 步：让 AI 开始写代码（Execute 阶段）

点击 Crew 面板的「🤖 让 AI 执行」按钮，或者说：

```
开始执行
```

AI 会依次：
1. 创建 `LoginPage.tsx`（你能看到代码在聊天流中出现）
2. 创建 `auth.ts`
3. 创建 `authStore.ts`
4. 修改 `App.tsx`

状态栏会显示「4 个文件改动」。

---

### 第 4 步：验证功能（Verify 阶段）

AI 完成后说：

```
运行测试，验证登录功能是否正确
```

AI 会：
1. 运行 `npm test` 或 `pytest`
2. 检查每条验收标准
3. 报告结果

**如果通过**：Crew 面板显示绿色，点击「归档」，完成！

**如果失败**：AI 会说类似：
```
验证失败：
- ✅ 验收标准1：邮箱格式验证正常
- ✅ 验收标准2：错误提示正常
- ❌ 验收标准3：JWT token 未正确存入 localStorage
开始修复...
```

然后自动进入 Iterate 阶段修复。

---

### 第 5 步（如需要）：迭代修复

AI 自动修复并重新验证。你不需要做任何事，等待即可。

如果 3 轮之后还没修好，AI 会说：
```
已超过迭代上限，创建阻塞项 [OPEN]。
建议：请检查 JWT_SECRET 环境变量是否已配置。
```

你根据提示处理后，说「继续」即可。

---

### 整个流程用时估计

| 阶段 | 用时 |
|------|------|
| Plan（确认验收标准） | 2-5 分钟 |
| Design（查看方案） | 1-2 分钟 |
| Execute（AI 写代码） | 3-10 分钟 |
| Verify（运行测试） | 1-3 分钟 |
| **合计** | **约 10-20 分钟** |

## 14. 常见新手问题

### Q：Plan 阶段 AI 生成的需求描述不对，怎么改？

直接在聊天框纠正：
```
proposal.md 的范围部分写错了，我不需要第三方登录，只要邮箱密码就够了
```
AI 会更新文件，然后再请你确认。

---

### Q：Execute 阶段 AI 写的代码风格我不喜欢，怎么办？

在执行前先设定技能，或直接告诉 AI：
```
所有组件用函数式写法，不要类组件；变量命名用驼峰；注释用中文
```

---

### Q：我切换了工作目录，Crew 工作区还在吗？

Crew 工作区的文件（`INSTRUCTIONS.md`、`crew.yaml`、`crew/`）保存在项目文件夹里，只要你回到同一个目录，工作区就还在。

---

### Q：一个项目可以同时进行多个 PDEVI 流程吗？

可以，每个变更是独立的目录：
```
crew/changes/
├── login-feature/
├── fix-bug-123/
└── new-dashboard/
```
三个可以同时进行，在 Crew 面板分别管理。

---

### Q：AI 改错代码了，想回退怎么办？

BYOE 不提供内置回退，但你可以：
1. 用 Git：`git diff` 查看改动，`git checkout -- <文件>` 回退
2. 告诉 AI：「刚才 auth.ts 的改动有问题，请恢复到改动前的版本」

**强烈建议**：使用 BYOE 前先 `git commit` 一次，保留干净基线。

---

### Q：关掉浏览器再打开，之前的进度还在吗？

在。PDEVI 的进度保存在项目目录的文件里（`proposal.md`、`design.md`、`resume.md`），不依赖浏览器缓存。重新 `byoe web` 后，AI 会自动加载这些文件继续工作。

---

### Q：可以不用 Web UI，纯命令行使用 PDEVI 吗？

可以：
```bash
byoe chat      # 进入命令行对话模式
# 然后正常用自然语言操作
```

## 15. 进阶技巧

### 技巧一：用 INSTRUCTIONS.md 约束 AI 行为

`byoe init` 创建的 `INSTRUCTIONS.md` 是给 AI 的全局规范，每次对话都会自动注入。你可以编辑它：

```markdown
## 技术栈
- 前端：React 18 + TypeScript + Tailwind CSS
- 后端：FastAPI + PostgreSQL
- 测试：pytest + vitest

## 代码规范
- 函数不超过 50 行
- 所有 API 必须有类型注释
- 禁止使用 any 类型

## 禁止事项
- 不要修改 config/ 目录下的文件
- 不要删除现有的测试
```

---

### 技巧二：结合专家智能体使用

在 Design 阶段切换到对应专家，获得更专业的技术方案：

```
# 做前端功能时
[切换到：前端专家]
帮我设计登录页面的组件结构

# 方案确认后，切换回通用助手执行
[切换到：通用助手]
按刚才的方案开始执行
```

---

### 技巧三：Prototype 模式快速验证想法

不确定方案可不可行时，先用 Prototype 快速跑通：

```bash
byoe plan "poc-redis-cache" --prototype
```

跑通后，再创建标准模式的正式变更：

```bash
byoe plan "redis-cache" --standard
```

---

### 技巧四：用自然语言查询进度

不需要记命令，直接问：

```
现在有几个活跃变更？哪个卡住了？
```

```
帮我总结一下 login-feature 做到哪一步了
```

---

### 技巧五：外部 AI 工具集成

在 Crew 工作区内使用其他 AI 工具时，BYOE 会自动注入 `INSTRUCTIONS.md`：

```bash
byoe run claude        # Claude 自动获得项目上下文
byoe run cursor        # Cursor 自动获得 .cursorrules
byoe run aider         # Aider 自动获得系统提示
```

这样所有 AI 工具都使用同一套项目规范，不会互相打架。

## 附录：PDEVI 文件结构一览

```
your-project/
├── INSTRUCTIONS.md              # 全局 AI 规范（自动注入）
├── crew.yaml                    # 项目配置
└── crew/
    ├── resume.md                # 当前进展摘要（AI 每次执行后更新）
    ├── blockers.md              # 待解决的阻塞问题
    ├── changes/                 # 活跃变更
    │   └── login-feature/
    │       ├── proposal.md      # P 阶段：需求分析文档
    │       └── design.md        # D 阶段：技术方案文档
    └── archive/                 # 已完成的变更（归档后移入这里）
        └── fix-bug-123/
            ├── proposal.md
            └── design.md
```
